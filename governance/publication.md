# Publication

Informative. How this repository is written today, why, and what has to be true before the specifications are written here.

## Today: two authorities, split by path

| Paths                                                                                        | Written                            | By                                                                                                                                                                                                   |
| -------------------------------------------------------------------------------------------- | ---------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `protocols/`, `docs/spec/`, `test-vectors/`, `README.md`, the license files, `PROVENANCE.md` | In the steward's source repository | An export: a script copies the files byte for byte, removes Markdown links to files that are not published, and writes `PROVENANCE.md` with the source commit and the SHA-256 of every file it wrote |
| `rfcs/`, `governance/`, `conformance/`, `CONTRIBUTING.md`                                    | **Here**                           | Pull requests, under [RFC 0001](../rfcs/0001-standards-process.md)                                                                                                                                   |

The export proposes its result as a pull request here; a maintainer merges it. Nothing reaches `main` except by pull request.

### What protects each side from the other

1. **The export cannot write here.** Its list of paths written in this repository is fixed in its source. It refuses to run if any file it would export falls on one of them.
2. **The export replaces only what it writes.** It removes and rewrites the exported files and leaves every other file exactly as it is.
3. **The drift check ignores this side.** The steward's daily comparison of this repository with what its source would export does not compare these paths, so a change here is never reported as drift to be "corrected".
4. **`PROVENANCE.md` says what it covers.** It lists what the export wrote and states that the paths written here are not in it.
5. **This side cannot silently change a specification.** An exported file edited here would be overwritten by the next export, and the drift check would report it first. That is intended: see below.

### What a contributor should expect

- A pull request to `rfcs/`, `governance/`, `conformance/` or `CONTRIBUTING.md` is reviewed and merged here.
- A pull request that edits a specification or a vector is **not merged as it is**, because the next export would overwrite it. It is treated as the proposal it is: an editorial fix is applied at the source and arrives with the next export, crediting its author; anything else follows RFC 0001, section 4.

## Why not write everything here now

Because the expectations in the vectors are generated by the Scala reference implementation, which is not public. If the specifications were edited here:

- a changed rule could not be given vectors by anyone outside the steward;
- nothing would check that the text here and the generator there still agree;
- the invariant that matters most, that a published expectation is never changed, would rest on review alone instead of on a byte-for-byte check.

Splitting by path gives the public process a place that cannot be overwritten, without weakening that check.

## The path to the specifications being written here

Each step is a precondition for the next. None is promised by a date.

| Step                                    | What it means                                                                                                                                                 | Who can do it                                                                                               |
| --------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------- |
| **1. Public process** (done)            | RFCs, governance and conformance reports are written here and survive every export                                                                            | —                                                                                                           |
| **2. Publish what is normative** (done) | The Lean definition that Work Contract Language 1 defers to is published under `formal/lean` and checked by this repository's CI                              | —                                                                                                           |
| **3. Remove private references**        | Specifications stop naming modules, scripts and decision records that readers cannot see; status paragraphs about one product move out of normative documents | An editorial pass, at the source                                                                            |
| **4. A public way to check the corpus** | A public implementation, or the public ones together, reproduce every vector in this repository's own CI, so that a pull request here is checked here         | Any implementer; `verified-cli` covers most of it today                                                     |
| **5. A public way to generate vectors** | Vectors for a new rule can be produced by a tool anyone can run                                                                                               | The steward publishes a generator, or the process accepts hand-built vectors checked by two implementations |
| **6. Specifications written here**      | The export is retired for specifications. The source repository becomes one implementation among others                                                       | An RFC that changes RFC 0001, section 11                                                                    |

Until step 6, a specification changes here only by an export that carries out an accepted RFC or an editorial fix.
