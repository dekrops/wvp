# RFC 0010: wvp is the source

|            |                                                                                                       |
| ---------- | ----------------------------------------------------------------------------------------------------- |
| RFC        | 0010                                                                                                  |
| Status     | Review                                                                                                |
| Author     | Zin Nam                                                                                               |
| Created    | 2026-11-18                                                                                            |
| Affects    | RFC 0001, section 11; `governance/publication.md`. No specification, version, vector or proof changes |
| Supersedes | Nothing                                                                                               |

The specifications, vectors, examples and Lean definitions are written in this repository from now on, and the export from the steward's source repository is retired. RFC 0001's section 11 is replaced, and a rule for publishing a vector that no reference implementation generated is adopted. This is for everyone who proposes, implements or relies on a change to the protocol.

## Motivation

RFC 0001, section 11, says specification text and vectors are written in the steward's source repository and arrive here by an export. On 2026-11-17 the steward repurposed that repository for other work. The code that generated the vectors and ran the export was removed from it, and is kept only in its tag `legacy-platform-2026-11`. Nothing is exported here any more, and nothing can be: there is no source left to export from.

Section 11 therefore describes a route that no longer exists. Without a change, no accepted RFC can be carried out. RFC 0003 (WVP v0.3) and RFC 0008 (Work Contract Language 2) are both waiting for a way to become specification text.

`governance/publication.md` planned the move as milestone C, one specification at a time, after milestones A and B. That plan assumed the source would stay. It did not, so the move happens at once, before every planned prerequisite is met. This RFC says which are not met and what stands in for each.

## What changes

**1. Section 11 of RFC 0001 is replaced.** The new section will say:

- Specifications, vectors, examples and the Lean definitions are written here, by pull request.
- An accepted RFC is carried out by a pull request here that names it. The specification's header names the RFC, and the RFC records the specification, version and commit that implement it, as before.
- Section 4 decides what each pull request needs, whichever path it touches. An editorial change is still a reviewed pull request; anything else still needs an issue or an RFC.
- The rule that a published expectation never changes (section 6, invariant 1) is enforced by the `unchanged` check on every pull request, as it is now.

The sentence saying that moving the specifications here "needs an RFC" is removed: this is that RFC.

**2. The provenance check is retired.** It compared each exported file with `PROVENANCE.md` and failed any pull request that edited one, so it cannot coexist with writing them here. `PROVENANCE.md` is kept, under a note, as the record of the last export. The `unchanged` and `structure` checks stay.

**3. A rule for vectors that no reference generated.** Until now every vector was generated by the steward's reference implementation, and that generator no longer runs. From now on:

> A vector may be published when its generator is public and deterministic, and two implementations that share no code with the generator or with each other reproduce it. Where only one does, the vector is published marked as singly reproduced, and it does not count toward Final (section 8.2).

This is the rule `governance/publication.md` proposed for milestone B, adopted here unchanged.

**4. `governance/publication.md` is marked superseded** by this RFC. It is kept as the record of the plan.

## Outcomes that change

None. No specification, version, vector, example or proof changes, and `unchanged` reports every published file identical. What changes is where a change is written and what a new vector needs.

## Compatibility

- **Implementers** see no change in any published file. A new vector now says whether it was reproduced by two implementations or by one.
- **Contributors** open pull requests against every path, under section 4, instead of having specification changes applied at the source.
- **Accepted RFCs** that mention the export in their own text (RFC 0002, RFC 0006) are not edited: after acceptance an RFC changes only to record its status. Their mentions of the export describe how things stood when they were accepted.

## Security considerations

- **Who can change a published expectation:** no one. The `unchanged` check fails any pull request that alters a published vector or its expected outcome, as before.
- **Who can add one:** a maintainer, by a pull request, under rule 3. With one maintainer and one main public implementation, a wrong vector could be published and marked singly reproduced. Such a vector cannot count toward Final, and a second implementation that disagrees with it is reported under section 4.
- **What is lost:** the byte-for-byte comparison against a regenerated corpus at each export. It is replaced by `unchanged` (published files never change) and by reproduction in public implementations (new files must be reproduced).

## Formal semantics

Nothing here is formal. The Lean definitions move with the rest and are checked by the same workflow.

## Alternatives

- **Keep the export.** There is no source left to export from. Restoring the removed code to keep the export alive would keep a private repository as the protocol's source for no other reason.
- **Freeze the protocol until milestone C's prerequisites are met.** RFC 0003 and RFC 0008 would wait for a second implementation by other authors, which has no date.
- **Move one specification at a time, as planned.** That plan relied on both repositories holding the files during the move. Only this one does.
