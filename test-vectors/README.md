# Shared protocol vectors

`canonical-hash-v1.json` is a language-independent fixture consumed directly by Scala's `SharedVectorsSuite` and Rust's `tests/golden.rs`. Each valid case carries raw input JSON text, expected canonical UTF-8 text and its SHA-256 digest. Tests independently parse and canonicalize the input, compare bytes, then compare hashes. Invalid cases must fail parsing or canonicalization.

The version is **verified-json-v1**, not RFC 8785. Existing Scala encoding and frozen ledger fixtures remain unchanged:

- Objects sort keys recursively by UTF-16 code-unit order (JVM string order).
- Arrays retain order and nulls remain present.
- Numbers must be mathematically integral and serialize in plain decimal, without leading zeroes or a negative zero. No floating-point rounding is allowed.
- Strings contain Unicode scalar values; unpaired surrogates in values or keys are rejected. No Unicode normalization occurs.
- Encoding is UTF-8, with no BOM or insignificant whitespace. JSON escaping uses short escapes for backspace, tab, newline, form feed and carriage return; all remaining characters in U+0000–U+001F and U+007F–U+009F use lowercase `\u00xx`. This applies to both keys and values; U+00A0 stays unescaped. Quotes and backslashes escape, ordinary slashes do not.
- Duplicate keys are outside the object model; these fixtures do not define duplicate-key parsing behavior.

Coverage includes nested key sorting, number spellings, arbitrary precision, array order, control escaping, supplementary-plane key ordering, non-normalization, library-marker-like object keys and an order observation. JSON strings preserve exact number spellings in the inputs; don't parse/reserialize them when editing fixtures. Add vectors when fixing compatibility bugs. Changing established canonical bytes needs a new protocol version and compatibility decision, not regenerated golden expectations.

Run `sbt 'crypto/test'` and `(cd crates && cargo test --workspace --locked)`. Normal `sbt test` also runs the vectors. CI requires both implementations to agree with the same fixture. Agreement on these cases is evidence of interoperability, not a proof for every possible object. Future claim/evidence/verification examples and Lean-derived checks belong here when their protocols are defined.

## Evidence statements

`evidence-statement/v1/` is the conformance corpus of [Verified Evidence Statement v1](../docs/spec/evidence-statement-v1.md): `valid/`, `invalid/` (not a well-formed statement) and `must-reject/` (well-formed but unacceptable) vectors of kind `statement`, `chain` or `admission`, plus `keys.json` with deterministic public test keys. Each vector is self-contained: trust registry, exact input text and expected outcome — canonical bytes and digests, chain summary, evidence-manifest digest and verification status, or the first rejection code. `valid/admission-authentic-agent-trace-is-insufficient` and `valid/admission-authentic-contradiction` pin that authentic evidence is not a verified claim.

The files are generated by `verified.protocol.GenerateVectors` and checked byte for byte by `ConformanceSuite`. `npm run test:conformance` runs an independent JavaScript implementation that must reproduce every evidence-layer outcome and re-derives the keys from their seeds; Rust's `tests/evidence_statement.rs` reproduces canonical bytes and digests. Never regenerate published expectations; a change in outcome is a new protocol version.

## Work Verification Protocol

`wvp/v0.1/` is the conformance corpus of [Work Verification Protocol v0.1](../protocols/wvp/v0.1/SPEC.md): `valid/` (accepted, whatever the decision), `must-reject/` (well-formed but refused) and `invalid/` (not a well-formed package). Each vector is self-contained: a trust registry or none, the exact package text, and the expected report or first refusal code. A valid vector can carry a `CONTRADICTED` or `UNDETERMINED` decision.

The files are generated by `verified.portable.GenerateWorkVectors` from the evidence-statement corpus's keys and statements, and checked byte for byte by `WorkPackageSuite`. `npm run test:conformance` runs the JavaScript implementation, which must reproduce every outcome, decisions included. Never regenerate published expectations.

`wvp/v0.2/` is the corpus of [protocol v0.2](../protocols/wvp/v0.2/SPEC.md), in the same format: packages whose contract is written in Work Contract Language 1. It is generated by `verified.portable.GenerateContractPackageVectors`, checked byte for byte by `ContractPackageSuite`, and reproduced by the JavaScript implementation.

## Work contracts

`work-contract/v1/cases/` is the conformance corpus of [Work Contract Language 1](../protocols/work-contract/v1/SPEC.md). Each file holds a `description`, a `contract`, an `environment` and the `expected` result: a decision with one value per requirement, or a refusal code. The cases cover the three decisions, every refusal, both conflict policies, ignored records, completeness and the cutoff, the truth tables (`60-*`), and the invoice-processing example.

`work-contract/v1/differential/` holds generated batches (`contract`, `cases: [{ environment, expected }]`): random subsets and distortions of the example's records, including ones that must be refused, produced from fixed seeds.

The files are generated by `verified.contractlang.GenerateContractVectors` and checked byte for byte by `ContractLanguageSuite`, which also states the decisions of the invoice scenarios by hand so that the corpus is not its own only witness. The Lean reference evaluator (`formal/lean`, run by `tooling/check-lean.sh`) and the JavaScript evaluator (`tooling/work-contract.mjs`, run by `npm run test:conformance`) must each reproduce every expected outcome in both directories. Never regenerate published expectations.

## Work units

`work-unit/v1/vectors.json` pins the identities and nullifiers of [work-unit identity v1](../protocols/work-unit/v1/SPEC.md) under three public test keys. It is generated by `verified.crypto.GenerateWorkUnitVectors`, checked by `WorkUnitSuite`, and reproduced by `tooling/work-unit.mjs`. Never regenerate published expectations.

## Claim registration

`claim-registration/v1/` is the conformance corpus of [claim registration v1](../protocols/claim-registration/v1/SPEC.md). `vectors.json` holds the public test keys, the relying party's trust configuration and registrations (agreement, claim and receipt) with their facts or first refusal. `log.json` holds runs of a registry's log and held receipts; `audit.json`, `notice.json` and `dispute.json` hold whole logs with the documents they name and each claim's state; `unit.json` holds checks of a claim's unit against its inputs. `head.json` holds heads, alone and against held entries, segments and other heads. They are generated by the test corpora of `modules/claim-registration`, checked byte for byte by its suites, and reproduced by `tooling/claim-registration.mjs`. Never regenerate published expectations.

## Work relation

`work-relation/v1/` is the conformance corpus of [work relation v1](../protocols/work-relation/v1/SPEC.md). `vectors.json` holds, for each case, relations (a signed statement and its body), record texts with the kind each is offered as, the reader's trust registry, and the reading they must yield: each record's reference or error, each relation's standing, each derived same-claim result and each stream's completeness. It is generated by the test corpus of `modules/work-relation` and checked byte for byte by its suite. No second implementation reproduces it yet.
